# 排行榜系统说明文档

## 1. 系统架构

### 1.1 核心组件

- **Master**：排行榜管理器，负责注册和启动排行榜
- **Bucket**：排行榜桶，每个桶对应一个排行榜，包含周期切换、数据清理、分页遍历等逻辑
- **Statement**：排行榜周期状态管理，包含分数格式化逻辑
- **Handle**：排行榜处理接口，提供获取当前期数和过期时间的方法

### 1.2 数据存储

- **Redis ZSet**：存储排行榜数据，支持按分数排序
- **Redis Hash**：存储排行榜结算状态，字段为周期值，值为结算状态(0-未结算，1-已结算)

### 1.3 主要文件结构

| 文件名       | 主要功能                         | 关键方法/函数                                  |
|------------|------------------------------|-------------------------------------------|
| bucket.go  | 排行榜桶管理，包含周期切换、数据清理、分页遍历等逻辑     | start, Cycle, ZAdd, ZRank, ZPage, Range, changeCycle |
| module.go  | 排行榜系统初始化，设置 Redis 客户端、开服时间等      | Start, GetBucket, Register                |
| service.go | 排行榜对外接口（ZAdd, ZRank, ZPage 等）      | ZAdd, ZRank, ZPage, ZRange                |
| statement.go | 排行榜周期状态管理，包含分数格式化逻辑        | formatScore                               |
| master.go  | 排行榜管理器，注册和启动排行榜              | Register, start, heartbeat                |
| submit.go  | 排行榜结算逻辑                      | checkUnsettledRanks, maySubmit, changeCycle |

## 2. 核心功能

### 2.1 排行榜管理

- **注册排行榜**：通过 `Register` 函数注册排行榜，指定名称、最大数量、初始分数、排序类型和处理函数
- **获取排行榜**：通过 `GetBucket` 函数获取指定名称的排行榜

### 2.2 分数管理

- **设置分数**：通过 `ZAdd` 函数设置排行榜分数，使用最终值，而不是增量
- **批量写分**：`ZAdds` 往【正在用的活榜】里成百上千条地写（定时全量重算、批量补人、GM 修正）
- **预置榜单**：`ZPreset` 【从空建起】一整份榜单，也是唯一写得进还没开始那一届的入口。
  分界是「目标榜空不空」，见 [5.3.1](#531-三个写入口的分工zadd--zadds--zpreset)
- **夺取席位**：`ZSwap` 用于名次即席位的定容榜，见 [5.3.2](#532-夺取席位zswap)
- **获取分数**：通过 `ZRank` 函数获取个人名次，支持是否返回分数

### 2.3 周期管理

- **切换周期**：当当前周期结束时，自动切换到下一个周期
- **检查未结算周期**：在启动时检查 Redis hash 表中是否有未结算的排行榜

### 2.4 结算管理

- **结算排行榜**：当周期结束时，自动结算排行榜
- **删除结算记录**：结算完成后删除 hash 表中对应周期字段

### 2.5 分页管理

- **分页获取数据**：通过 `ZPage` 函数分页获取排行榜数据，支持自定义每页大小

## 3. 技术实现

### 3.1 分数格式化

- **降序排行榜**：分数 = 原始分数 + 剩余时间，确保相同分数的玩家按时间排序
- **升序排行榜**：分数 = 原始分数 + 已用时间，确保相同分数的玩家按时间排序
- **错误处理**：解析失败时返回原始分数，避免排行榜数据异常

### 3.2 并发安全

- **互斥锁保护**：在处理 `submits` 切片时使用互斥锁保护，确保并发操作的安全性
- **注意事项**：排行榜在程序启动时初始化，不需要使用竞态保护

### 3.3 错误处理

- **初始化错误**：正确返回 `Master.start()` 的错误，确保初始化失败时能够向上层报告
- **时间解析错误**：添加对 `time.Parse` 错误的捕获，避免初始化失败
- **分数格式化错误**：添加对 `strconv.ParseFloat` 错误的捕获，避免排行榜数据异常
- **Redis 操作错误**：捕获并处理 Redis 操作错误，确保系统的稳定性

### 3.4 分页逻辑

- **循环条件**：使用 `paging.Page <= paging.Total` 作为循环条件，确保分页遍历的正确性
- **分页计算**：通过 `(paging.Page - 1) * paging.Size` 计算起始位置，`s + paging.Size - 1` 计算结束位置

### 3.5 结算记录存储

- **存储方式**：使用 Redis hash 表存储结算状态，字段为周期值，值为结算状态(0-未结算，1-已结算)
- **删除策略**：结算完成后使用 `HDel` 删除 hash 表中对应周期字段，减少 Redis 键数量

### 3.6 时间单位一致性

- **Redis 过期时间**：使用 `7*24*time.Hour` 表示 7 天，与 Redis 的过期时间单位一致

## 4. 修复的问题

### 4.1 并发安全问题

- **问题**：在处理 `submits` 切片时没有使用互斥锁保护，可能导致并发修改切片的问题
- **修复**：在 `checkUnsettledRanks` 函数中添加互斥锁保护对 `this.submits` 切片的访问

### 4.2 错误处理问题

- **问题**：`Start` 函数忽略 `Master.start()` 返回错误，直接返回 nil
- **修复**：修改为正确返回 `Master.start()` 的错误，确保初始化失败时能够向上层报告

### 4.3 分页逻辑问题

- **问题**：`Range` 函数的循环条件使用 `i < paging.Total` 导致遍历不完整或无限循环
- **修复**：修改为使用 `paging.Page <= paging.Total` 作为循环条件，并在循环中递增 `paging.Page`

### 4.4 结算记录存储问题

- **问题**：每个周期使用独立 Redis key 存储结算状态，导致键数量过多
- **修复**：改为使用 Redis hash 表存储结算状态，字段为周期值，值为结算状态(0-未结算，1-已结算)

### 4.5 时间单位一致性问题

- **问题**：检查 Redis.Expire 过期时间和 time.Hour（纳秒）是否一致
- **验证**：`7*24*time.Hour` 表示 7 天，与 Redis 的过期时间单位一致

```go
// 初始化排行榜系统
err := rank.Start(redisClient, "shareId", 1)
if err != nil {
    log.Fatalf("初始化排行榜失败: %v", err)
}
```

### 5.2 注册排行榜

```go
// 注册排行榜
rank.Register("daily", 100, 0, rank.SortTypeDesc, handle)
```

### 5.3 设置分数

```go
// 设置排行榜分数
err := rank.ZAdd("daily", cycle, "uid1", 100)
if err != nil {
    log.Errorf("设置排行榜分数失败: %v", err)

```

### 5.3.1 三个写入口的分工：ZAdd / ZAdds / ZPreset

| | 定位 |
|---|---|
| `ZAdd` | 单条，**玩家写分** |
| `ZAdds` | 批量，往**活榜**里写（定时全量重算 / 赛季中批量补人 / GM 批量修正 / 分批拼榜的后续批次） |
| `ZPreset` | 整份，**从空建起**（换届填充 / 预置还没开始的那一届） |

**`ZAdds` 与 `ZPreset` 的分界就一句话：目标榜空不空。**

|  | `ZAdds` | `ZPreset` |
|---|---|---|
| 对目标榜的要求 | **非空**，往活榜里增量合入 | **必须为空**，否则 `ErrPresetNotEmpty` |
| 写哪一届 | **只能当前届**，否则 `ErrCycleExpired` | 指定届，**含还没开始的下一届**（`cycle` 必须显式传，不接受 0） |
| 写入方式 | 直接 `ZADD` 目标键，按 `zAddsChunk=1000` 分片 | 写临时键 `<key>-preset`，最后 `RENAMENX` 原子搬过去 |
| 中途失败 | 已写的分片**留在榜上**（半填） | 目标键仍是空的，临时键删掉 |
| 过滤 | `isScore` 入围分 + `isMax` 守门员裁剪 | 只 `isScore`，**不做 isMax** |
| 空列表 / 全被过滤 | 返回 `(0, nil)`，无害 | **报错** |

`ZPreset` 靠 `RENAMENX` 要求目标榜为空，所以它做不了「往已有的榜里补人 / 改分」
——那正是 `ZAdds` 不可替代的地盘：战力榜、等级榜这类**分数来自玩家档案而不是主动打分**
的榜，通常由定时任务全量重算写入，榜一直是非空的。反过来，一次性从空建满整份榜
优先 `ZPreset`：它中途失败不会留下一张半填的活榜（见下）。

🔴 **`isMax` 那条差异不是随手配的**：往活榜里批量写必须尊重当前届的 `zKeeper`（末位分数），
否则会冲破 `zMax`；而空榜压根没有 keeper，`ZPreset` 拿当前届的去卡是张冠李戴。
这条差异与「活榜 vs 空榜」一一对应。

🔴 **不要让 `ZPreset` 在榜非空时自动降级成 `ZAdds`。** `ZSwap` 合并 `ZTakeover` 的理由
在这里恰好反过来：那边的判据「a 在不在榜」是**外部状态**，查完就变、业务判不准，
所以必须挪进 Lua；这边的判据是**调用方的意图**——「我要从空建起，榜非空说明出事了」。
`ErrPresetNotEmpty` 的全部价值就在于它会失败：自动降级会把「覆盖了一张正在用的榜」
这个事故变成静默的成功，玩家名次凭空重排，而调用方拿到 nil。

**两者都不受休战约束**，受约束的是玩家驱动的 `ZAdd` / `ZSwap`，
见 [6.6](#66-休战期可选接口-handletruce)。

⚠️ 判据是「目标榜**为空**」而不是「必须是未来届」：结算窗口若贴在日初，换届那一刻新一届
**已经是当前届**了，但榜还空着，正需要预置；用「必须是未来届」去卡会把这条正常路径一并否掉。

三个实现差异都有原因：

- **临时键 + `RENAMENX`，不直接写目标键。** 整批 5000 条要分多次 `ZADD`，中途失败直接写
  就留下一张只填了一半的**活榜**——而它非空，业务侧的「榜空即补」兜底不会触发，这一届永久缺人。
  `ZAdds` 没这个顾虑：它本来就是往已有的榜上增量合入，半填不构成特殊状态。
  用 `RENAMENX` 而不是「先 `EXISTS` 再 `RENAME`」，是因为两步之间别的进程可能刚把榜建好，
  那一瞬的覆盖是最难查的一类事故（名次凭空重排，且只在并发时偶发）。
- **不做 `isMax`。** `zKeeper`（末位分数）是**当前届**的，目标届还没开始、根本没有 keeper，
  拿当前届的去卡新榜是张冠李戴。
- **Statement 是临时造的。** 目标届可能还没开始，`this.statement()` 拿不到，只能按
  `handle.Expire(cycle)` 算出的起止时间 `NewStatement` 一个。副作用在 tiebreak：
  `formatScore` 的小数位依赖「本届已过时间占比」，届未开始时 `elapsed` 为负、被钳到 0
  ——即全体同分先到先得的初值，正是预置该有的语义。`ZAdds` 用的是真实 elapsed。

**怎么选：**

| 场景 | 用 |
|---|---|
| 榜正在用，单个玩家打了分 | `ZAdd` |
| 榜**非空**，系统批量加人 / 批量改分 / 定时重算 | `ZAdds` |
| 榜**为空**，要把整份榜单建起来 | `ZPreset`（崩溃安全） |
| 一届**还没开始**就要把榜摆好 | `ZPreset`（唯一走得通的） |
| 在休战/冻结窗口里写 | `ZAdds` / `ZPreset` 都放行；`ZAdd` / `ZSwap` 被拦 |

🔴 `ZAdds` 与 `ZPreset` 都**显式报错**，不像单条 `ZAdd` 那样静默返回 nil。批量写的调用方
多半在建榜：静默不写会留下一张空榜、调用方却以为填好了，之后所有「取我上方/下方的对手」
全部取空。`ZSwap` 当初也是为同一个理由没有沿用静默语义。

### 5.3.2 夺取席位（ZSwap）

用于**名次即席位的定容榜**（角斗场之类）：a 挑战成功后坐上 b 的名次。

```go
r, err := rank.ZSwap("arena", cycle, atkUid, defUid, rank.SwapIfTargetAhead)
switch {
case errors.Is(err, rank.ErrSwapMemberMissing):
    // b 不在榜:席位不存在(退榜/换届),无从夺取
case errors.Is(err, rank.ErrSwapCondition):
    // b 名次不比 a 靠前,不构成"往上打"
case errors.Is(err, rank.ErrSwapEqualScore):
    // 双方同分,互换是 no-op
case errors.Is(err, rank.ErrTruce):
    // 休战期只读
case err != nil:
    // Redis 故障等
default:
    if r.Kind == rank.SwapKindTakeover {
        // a 原在榜外:已顶入,b 被挤出榜 -> 发邮件通知 b、清它的名次缓存
    }
    // r.ScoreB 是 a 接手到的分数;r.ScoreA 仅 SwapKindSwap 时有意义
}
```

**b 必须在榜，a 在不在榜都合法**，由 Lua 自己查、自己分派：

| a | b | 结果 |
|---|---|---|
| 在榜 | 在榜 | `SwapKindSwap` —— 互换分数，b 退到 a 原来的名次 |
| 榜外 | 在榜 | `SwapKindTakeover` —— a 接手 b 的名次，b 出榜 |
| 任意 | 榜外 | `ErrSwapMemberMissing` |

🔴 **不要自己先查 a 在不在榜再决定怎么调**——查不准。判据只能在调用**之前**查，而查完到调用落地之间 a 可能刚被 `ZAdd` 进榜，也可能被溢出裁剪（`ZCARD > zMax+OverflowThreshold` 时由心跳触发的 `ZRemRangeByRank`）静默挤出去。这正是 `ZTakeover` 被并进 `ZSwap` 的原因：判断和写入必须同处一个原子块。

⚠️ **只适用于定容榜。** 榜没满时 a 顶掉 b 会静默发生——明明还有空位，b 却被挤出榜。容量没满、该让人直接上榜的场合请用 `ZAdd`。

⚠️ `SwapIfTargetAhead` 比的是**名次**不是分数（降序取 `ZREVRANK`、升序取 `ZRANK`，出来的 rank 恒「越小越靠前」），所以升降序两种榜共用一个比较符。a 在榜外时不参与判定，视为「排在所有人之后」，条件恒成立。

## 6. 注意事项

### 6.1 并发安全

- 在多线程环境下，排行榜系统已经通过互斥锁保护了关键操作，确保并发安全

### 6.2 错误处理

- 系统已经完善了错误处理机制，避免了初始化失败、时间解析错误、分数格式化错误等导致的系统异常

### 6.3 性能优化

- 结算记录存储使用了 Redis hash 表，减少了 Redis 键数量，提高了查询效率
- 分页遍历逻辑已经修复，确保所有玩家数据都能被处理

### 6.4 时间单位

- Redis.Expire 过期时间使用了 `7*24*time.Hour` 表示 7 天，与 Redis 的过期时间单位一致

### 6.5 结算机制

- 切换周期时会将上一届状态写入 Redis hash 表，启动时会检查未结算的排行榜
- 结算完成后会删除 hash 表中对应周期字段，减少 Redis 键数量

### 6.6 休战期（可选接口 HandleTruce）

榜可以有一段「只读」的窗口，通常用来做结算：期间不接受任何写入。

**不需要休战期的榜什么都不用做**——`Handle` 里没有这一项，实现 `HandleTruce` 才启用：

```go
type HandleTruce interface {
    Truce(cycle int64) bool // true = 当前处于休战期
}
```

**什么时候算休战完全由榜自己决定**，框架只问一句「现在休不休战」。
老的「本届结束前 X 秒」照样写得出来：

```go
func (h *xxx) Truce(cycle int64) bool {
    _, e := h.Expire(cycle)
    return time.Now().Unix() >= e-300 // 届末 5 分钟
}
```

也能写出旧签名表达不了的形状，比如「届是周、休战每天来一次」：

```go
func (h *xxx) Truce(int64) bool {
    return time.Since(todayStart()) < time.Minute
}
```

> **为什么把 `Truce() int64` 换掉**：返回秒数只能表达一种固定形状(一届一次、贴着届末)。
> 遇到形状不同的需求，业务只能绕开框架自己判，于是 `Writable()` 这类框架接口
> 再也反映不了真实状态——框架以为可写，业务早就拒绝了。

🔴 **休战约束的是「改变名次」，不是「建立榜单」：**

| | 接口 | 休战期 |
|---|---|---|
| 玩家驱动 | `ZAdd`（写分）· `ZSwap`（席位争夺） | **被拦**，显式报错 `ErrTruce` |
| 系统驱动 | `ZAdds`（活榜批量写）· `ZPreset`（从空建榜） | **放行** |

系统写榜恰恰发生在休战窗口里——换届冻结 → 结算 → 把新一届填好、定时重算全服分数，
都是同一段时间里的事。若 `ZAdds`/`ZPreset` 也判休战，它们在自己的正经用途上永远返回 `ErrTruce`。

⚠️ 反过来说，`ZAdds` 因此**没有保险**：拿它做玩家驱动的批量写入（如「结算时批量补分」）
会绕过休战。那类写入一律走 `ZAdd` / `ZSwap`。

被拦的两条一律**显式报错**而非静默丢弃：静默失败是个长期的坑——玩家扣了票、发了奖、
分数却没写进去，而调用方拿到 nil 以为成功，日志里什么都看不到。

`ZAdd` 此前在休战期是**静默返回 nil**，那是个长期的坑：玩家扣了票、发了奖、分数却没写进去，
而调用方拿到 nil 以为成功，日志里什么都看不到。现已与其余两个接口对齐。
**升级注意**：如果你的榜有休战期且业务把 `ZAdd` 的返回值当"恒为 nil"用，现在会拿到错误——
这正是要修的地方，别用 `_ =` 吞掉。

## 7. 总结

排行榜系统是一个功能完整、性能优化、并发安全的系统，支持多种排行榜类型、周期管理、结算管理和分页管理。系统已经修复了并发安全、错误处理、分页逻辑、结算记录存储等问题，确保了系统的稳定性和可靠性。

通过本系统，开发者可以方便地实现各种排行榜功能，如日榜、周榜、月榜等，支持按分数排序、按时间排序等多种排序方式，满足不同游戏的需求。
